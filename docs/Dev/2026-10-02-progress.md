This document records the working Faraday learning loop and the fixes completed today.

- A signed-in visitor opening `/` is redirected to `/dashboard`.

## Start a Topic flow

1. The student enters a main topic.
2. Faraday asks one short level question: brand new, knows a little, or revising.
3. Grade, teaching style, response format, and pilot consent are collected only for the first profile setup.
4. Faraday starts with foundations and returns a large introduction plus 3–4 ordered teaching cards.
5. Each card contains one small concept, a short explanation, and a concrete example.
6. `I understood` automatically selects and teaches the easiest next subtopic.
7. `I'm confused` automatically submits a request to re-teach the same part using simpler words and a different example.
8. The follow-up input remains beneath the newest answer.
9. After enough understood steps, the lesson becomes completed and remains available for review.

## Visible conversation history

Lesson turns are stored in `lesson_turns` and returned when a student resumes a session. The lesson screen renders the previous student messages and their matching Faraday card responses in chronological order. Only the newest response displays feedback buttons and the follow-up input.

Raw turns expire after 90 days. The compact session summary, concept progress, profile, and safe memories remain until the student deletes their Faraday learning data.

The refresh bug that paired the original topic with the newest AI response was fixed. Restore now uses the latest saved student message that actually belongs to the saved teacher response. Refreshing does not generate a new model response.

## Lesson progress header

An active session becomes a focused lesson screen rather than continuing to look like the topic-entry page. A sticky, full-width progress header remains visible while responses scroll.

- Completed subtopics are fully green.
- The current AI-taught subtopic is half filled until the student confirms understanding.
- Confused/re-taught responses do not falsely complete a subtopic.
- Future subtopics remain unfilled.
- Segment widths automatically adapt to the number of visible subtopics.
- A large percentage summarizes the currently discovered learning path.

The dashboard sidebar was reduced from 278px to 224px, with smaller navigation controls, so the lesson workspace has more room.

## AI response contract

Groq must return strict, non-streaming JSON matching this shape:

```json
{
  "teacherMessage": "Let's start with the easiest idea.",
  "lessonTitle": "Motion basics",
  "cards": [
    {
      "id": "motion-meaning",
      "title": "What is motion?",
      "body": "Motion means that an object's position changes over time.",
      "example": "A football rolling across the ground is in motion.",
      "kind": "concept"
    }
  ],
  "nextTopics": [
    {
      "id": "speed",
      "label": "Speed",
      "detail": "Learn how fast something moves."
    }
  ],
  "summary": "The learner began with the meaning of motion.",
  "memoryCandidates": []
}
```

The production schema requires 3–6 cards, 2–4 ordered next topics, and no more than three memory candidates. The prompt currently asks the model to keep lessons concise at 3–4 cards. Every result is validated with Zod before it is saved or rendered. Model-generated HTML is never rendered.

Supported student display preferences are:

- `visual_cards`
- `real_examples`
- `step_by_step`
- `video_style`

Supported teaching styles are sports, practical, story, space, game-like, and direct.

## Backend and database fixes

- Removed runtime dependence on the missing `student_profiles.preferred_format` and `learning_sessions.content_format` columns.
- Response-format preference is now stored as a private technical preference in the existing `student_memories` table and hidden from the normal memory list.
- Kept migration `202609300002_saved_teaching_preferences.sql` for migration-history compatibility; the application does not require its optional columns.
- Added `202610020001_restore_lesson_turns.sql` to repair projects where the base migration was only partially executed.
- Missing `lesson_turns` now degrades safely instead of blocking lesson generation, although running the repair migration is required for durable visible history.
- Added safer server-side error logging while keeping credentials and internal errors out of browser responses.
- Groq uses low reasoning effort, a 1,800-token bound, strict JSON schema, a 25-second timeout, and one retry for invalid/empty generation.
- The server sends only the relevant profile, active session summary, progress, safe memories, and four recent turns—not the entire raw history.
- The current per-user protection allows up to 12 lesson turns in 10 minutes.

## Database migration roles

- `202609300001_faraday_learning.sql`: creates the complete base schema for a new project.
- `202609300002_saved_teaching_preferences.sql`: preserved compatibility migration; its extra columns are optional for current code.

Migration files are offline source-controlled instructions. They change the hosted database only when applied with the Supabase CLI or run in Supabase SQL Editor.
